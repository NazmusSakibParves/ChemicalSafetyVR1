## Architecture (small, central, data-driven)

### A. Content as data, one file per scenario, both languages in the same file
`Assets/Resources/Content/SC01.json ... SC22.json` (TextAsset; a later "remote override" can replace them without code changes).
```
{ "scenario": "SC01", "title": {"en": "...", "bn": "..."},
  "strings": { "instruction": {"en": "...", "bn": "..."}, "hint.touch": {...} },
  "questions": [ { "id": "SC01.Q1", "header": {...}, "prompt": {...},
      "options": [ { "id": "a", "text": {...}, "feedback": {...}, "wrongTitle": {...} }, ... ],
      "correct": "d", "correctTitle": {...}, "nextLabel": {...}, "shuffle": true } ] }
```
- Both languages in ONE file so English and Bangla cannot drift apart (the user's fear); option `id` (not position) is what is graded and reported.
- `Loc` static service: `Loc.Lang`, `Loc.T("SC01", "instruction")`, `Loc.Question("SC01.Q1")`. Missing key -> English fallback + a loud log + failing validator (never a silent blank).
- Editor menu **Chemical Safety/Content/Validate** (also part of the smoke test): every key has `en` and `bn`; option ids unique; exactly one correct; arrays the same length; each referenced voice clip exists in both languages; each Bangla string has its rendered image (see C).
- `ScNNContent.cs` constants are replaced by `Loc` lookups one scenario at a time. A one-time **golden master** tool dumps today's English strings (reflection over `ScNNContent`) to `Docs/Login/golden_en.json`; after migration the `en` side of the JSON must equal it byte for byte, so English stays identical.

### B. Voice by language
- Clip naming stays `VO_<Name>_bn` / `VO_<Name>_en`; one table `VoiceBank` (key -> bn clip, en clip) replaces the `PresentableArt.voXxx` pairs; `PlayVoice(key)` picks the clip for `Loc.Lang`. Generation stays in `generate_vo.py` (one Bangla voice, one English voice, same PRON rules; English voice = the one used now).
- Need NEW English clips for every line that today exists only in Bangla (instructions, hints, gates, correct/wrong, per-scenario lines). The completion line plays in the chosen language only; "training complete" only at SC22 (existing rule).
- Validator fails if a key has a clip in one language and not in the other.

### C. Bangla on-screen text (the one real technical risk)
TMP cannot shape Bengali. Options, decided by a short **spike (Phase 0)**:
1. *Runtime shaping*: test whether Unity 6000.6 (ATG / TextCore, or newer TMP/uGUI) shapes Bengali correctly in a world-space canvas on Quest. If yes: use it directly, JSON edits apply at runtime. Cleanest.
2. *Build-time rendering (fallback, proven in this project)*: menu **Chemical Safety/Content/Render Bangla Text** reads the JSON, renders every `bn` string to a PNG with the existing Pillow + Noto Sans Bengali pipeline (file name = key + hash of the text, so a changed text is detected), imports sprites, `Loc` returns sprites. Editing the Bangla JSON = edit + one menu click, still no code change. A `LocText` widget shows TMP text for English or an Image for Bangla (auto-fit to the same box), used by the MCQ panel, popups, hints, drum labels and subtitles so layouts do not change.
3. Native HarfBuzz plugin: only if 1 and 2 both fail (heavy, last resort).

### D. Option shuffle (anti-cheat) and grading
- `QuestionSession` is created when the question opens: permutation of option ids from a seeded RNG (`seed = hash(sessionId, questionId)`), generated once per scenario per session and kept for wrong retries inside the same visit (the order does not jump while the user retries). A new game or a new login gets a new seed.
- `PresentableMcqPanel.Question` keeps its API; the builder just hands it the already-permuted options and the new `correctIndex`; `Answered(index)` is mapped back to the option id. Everything tied to an option (feedback, wrong title, icons, overlays, SC03 drum highlight, SC07 win, SC06 fancy FX, SC01 drum picks) travels WITH the option, not with the slot.
- Audit before enabling per question: options that refer to each other by position ("both A and B", "all of the above", "none") must be marked `"shuffle": false` in the JSON (flag them in Phase 3 review with the user). Labels shown A/B/C/D follow the displayed slot.
- Smoke test: answers by option id (not index), runs several seeds, and asserts the correct slot varies.

### E. Session and results model (ready now, API later)
- `SessionData`: `client_submission_id` (GUID), participant name, e-mail, phone (normalised, one of the two may be empty), `language`, `device_id`, started/completed timestamps. Optional fields from the sample (organisation, batch, designation, notes) stay empty until the product needs them.
- `AttemptRecord` per scenario (`lesson_id` "SC01".., language, started_at, ended_at, score, max_score, passed, answers[]). `AnswerRecord`: question text as shown, options as `{A..D}` in the DISPLAYED order, `selected_option`, `correct_option`, `is_correct`, `time_ms`, `hint_used`, plus (needs the API owner's OK as extra fields) `wrong_attempts`, `option_ids_order`, `tries[]` (every selection with time). Marks rule (full mark only at first try? partial after retries?) is a product decision: ask.
- `ResultsStore` writes after EVERY answer to `persistentDataPath/results/<client_submission_id>.json` (crash/quit safe) and exports the final file in the sample's exact schema. `ISubmissionSink` (file now; HTTP with retry queue later, endpoint/auth from the user).
- Hooks are only in `RunQuestion` (answer/wrong/correct, time) and the scenario start/end; no flow change.

### F. Login screen
- New first stage of the Presentable scene (a `LoginStage` object built by the builder; `RunLogin` runs before `RunScenario1`). World-space canvas about 1.1-1.2 m in front of the spawn, centre slightly below eye height, about 1.0 m wide, tilted a few degrees, re-centred to the head yaw when shown (never closer than 0.9 m, never beyond arm reach 1.3 m).
- Look: the reference image (panel frame, neon cyan, WELCOME, user and envelope icons, START with glow, BENGALI | ENGLISH toggle, "Developed by BMQAS", partner logo bar). Generated with a `Tools/generate_login_ui.py` like the other UI generators; 3D animated background: lab backdrop, drifting ball-and-stick molecules, glowing tubes with bubbles, sparks, panel scan-line, START idle pulse.
- Language toggle: two-segment switch, default **ENGLISH**; the active side is filled/glowing with a check mark and a short slide animation, the inactive one dim; switching re-labels the whole login screen immediately and plays a soft click.
- Input: finger-only touch (no rays), so a custom **touch keyboard** (letters / digits-symbols pages, shift, backspace, `@` `.` keys, a numeric-friendly page for phone) rendered as world UI; editor keyboard also works. (Quest system keyboard via `TouchScreenKeyboard` is not used because it breaks the finger-only rule and the layout.)
- Validation (all messages localised, shown under the field, START re-validates):
  - Name: required, 2-60 chars, letters/space/`.`/`'`/`-` only; any digit (ASCII `0-9` or Bangla `০-৯`) is rejected, also blocked at typing time.
  - Contact: one field. If it contains `@` -> e-mail regex (`local@domain.tld`, no spaces). Else phone: remove spaces/`-`/`()`, convert Bangla digits, optional leading `+88` or `88` removed, then must be exactly 11 digits (`01` + operator digit 3-9 + 8 digits); fewer or more -> error ("number must be 11 digits, you entered N").
  - Pure functions (`LoginValidator`) with unit tests (EditMode) for the cases the user listed.
- Name is typed with a Latin keyboard first (Bangla typing needs shaping too; see open questions).

## Safety nets against breaking existing work
- Change only text/voice/data sources and the question order; no change to builders' geometry, animations, touch, or the flow chain.
- English output must stay identical (golden master + English smoke run); Bangla run must also reach `[SMOKE] DONE runtime errors/exceptions = 0`.
- One scenario per commit so a regression is easy to bisect; never touch `ChemicalSafety_Demo`.
